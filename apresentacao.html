Apache CouchDB vs. Couchbase Server

Da Sincronização Offline-First sobre HTTP à Performance Sub-Milissegundo em Memória Gerenciada

🌐 A Crise do RDBMS Clássico

  • Limites físicos da escalabilidade vertical (Scale-Up) na Web 2.0 e Mobile.
  • Impedância Objeto-Relacional: Custo de fragmentar agregados em dezenas de tabelas normalizadas.
  • Bloqueios pessimistas (2PL) inviáveis em topologias geograficamente distribuídas.

📄 O Paradigma Documental JSON

  • Documentos auto-contidos em JSON (Arrays e Objetos aninhados).
  • Localidade de Dados: Leitura de um agregado completo em um único I/O.
  • Evolução ágil de schema (Schema-on-read) sem ALTER TABLE bloqueante.

🪶 O Caminho do Apache CouchDB (ASF)

  • Projeto Top-Level da Apache Software Foundation desde 2008.
  • Manteve seu núcleo em Erlang/OTP focado em protocolo HTTP nativo e replicação Master-Master.

Slide 3 • Filosofia de Engenharia

Bifurcação Filosófica: Web Nativa vs. Performance Memory-First

Decisões opostas em protocolo de rede, controle de concorrência e hierarquia de memória

🟧 Apache CouchDB: "Sync & Web-First"

  • Protocolo Primário: HTTP/REST nativo (porta 5984). Qualquer browser ou cURL conversa direto com o banco.
  • Caminho de I/O: Disk-First (Append-Only). Toda escrita vai direto para estruturas imutáveis em disco.
  • Concorrência Otimista Explícita: Árvore MVCC no documento via _rev. Desenhado para desconexões.
  • Foco Principal: Resiliência em redes instáveis, sincronização Offline-First e topologia AP.

🟦 Couchbase: "Memory-First & Scale"

  • Protocolo Primário: Binário proprietário sobre TCP (porta 11210) com SDKs inteligentes cientes da topologia.
  • Caminho de I/O: Memory-First. Mutações gravadas imediatamente no cache gerenciado em RAM (sub-ms).
  • Consistência Forte por Padrão: Único vBucket ativo por chave (CP) + CAS otimista e transações ACID.
  • Foco Principal: Vazão extrema (milhões ops/s), latência em microssegundos e consultas SQL++ (N1QL).
Slide 4 • Arquitetura Interna Apache CouchDB

CouchDB: Motor Append-Only e Indexação B+Tree

Imutabilidade em disco, concorrência lock-free em Erlang e imunidade a corrupção

⚙️ Núcleo Erlang/OTP & Tail-Append

  • Construído em Erlang/OTP: processos leves (Actor Model) e tolerância a falhas (Let it crash).
  • Zero In-Place Updates: Blocos de disco jamais são sobrescritos. Novas revisões vão sempre para o fim do arquivo (.couch).
  • Tail Header: O cabeçalho com ponteiro para a raiz da B+Tree é gravado no final do arquivo após cada commit.

🛡️ Garantias e o Papel do Compaction

  • Leituras Lock-Free: Leitores percorrem snapshots imutáveis da B+Tree sem bloquear escritas.
  • Crash-Only Design: Em queda de energia, basta ler o arquivo de trás para frente até o último Tail Header válido.
  • Compaction: Reescreve o arquivo em background removendo blocos órfãos de revisões antigas.

Slide 5 • Controle de Concorrência no CouchDB

CouchDB: MVCC Explícito (_rev) e Árvore de Revisões

Como cada documento funciona como um mini-repositório Git para suportar conflitos distribuídos

🔐 Ciclo Optimistic Locking (_id + _rev)

  • Formato do _rev: <geração>-<hash_md5_determinístico>.
  • Regra de Escrita: O cliente deve enviar o _rev atual no PUT ou DELETE.
  • Se o _rev divergir da ponta da árvore no servidor: rejeição imediata com HTTP 409 Conflict.
  • Deleções geram uma revisão Tombstone ("_deleted": true) para propagar a exclusão na replicação.

🌿 Conflitos em Replicação Master-Master

  • Quando Nó A e Nó B editam o mesmo documento offline, a árvore bifurca (2-a... e 2-b...).
  • Eleição Determinística: Todos os nós escolhem a mesma revisão vencedora comparando geração e ordem ASCII do hash (sem depender de relógio NTP!).
  • A revisão perdedora fica preservada em _conflicts até a aplicação resolver e podar o ramo.

Slide 6 • Consultas e Replicação no CouchDB

CouchDB: Views MapReduce, Mango (_find) e _changes

Indexação incremental em B-Tree e o protocolo de replicação baseado em log de eventos

🗺️ Views MapReduce (_design/)

  • Funções JavaScript/Erlang salvas em Design Documents.
  • emit(key, value) alimenta uma B+Tree secundária incrementalmente.
  • Reduções (_count, _sum, _stats) ficam pré-computadas nos nós internos da B+Tree.

🥭 Mango Queries (POST /_find)

  • Introduzido no CouchDB 2.0+ (doado pelo IBM Cloudant).
  • Sintaxe declarativa em JSON ($eq, $gt, $in, $regex) sem escrever JS manual.
  • Consome índices B-Tree criados via POST /db/_index.

📡 O Endpoint /_changes

  • Exposição direta do log sequencial (update_seq) via HTTP (Polling, Long-Polling ou Continuous Stream).
  • Couch Replication Protocol: Lê _changes ➔ Calcula delta via _revs_diff ➔ Envia lote via _bulk_docs.

Slide 7 • Arquitetura Interna Couchbase Server

Couchbase: Arquitetura Memory-First e Particionamento por vBuckets

Cache gerenciado integrado, protocolo DCP e roteamento direto Single-Hop sem proxies

🚀 Caminho de Dados Memory-First (KV Engine)

  • Leituras e escritas ocorrem diretamente no Managed Cache em RAM (resposta em microssegundos).
  • DCP (Database Change Protocol): Fluxo binário em memória que propaga mutações assincronamente para:
    1. Replication Queue (RAM dos nós réplica).
    2. Persistence Queue (Motores Couchstore / Magma).

🧩 Particionamento Estático: 1024 vBuckets

  • Cada Bucket é dividido fixamente em 1024 vBuckets.
  • Fórmula determinística: vBucket = CRC32(Key) % 1024.
  • O SDK consulta o Cluster Map local: zero proxies intermediários (Single-Hop Routing direto ao nó dono do vBucket ativo).

Slide 8 • Escalabilidade Multi-Dimensional (MDS)

Couchbase: Arquitetura Multi-Service e Isolamento de Workloads

Eliminando o efeito "Noisy Neighbor" ao escalar RAM, CPU e I/O de forma independente

1. Data Service (KV)

  • Operações por chave (GET, UPSERT, SUBDOC).
  • Hardware Alvo: Servidores com alta densidade de RAM.
Uso de Memória RAM (Cache)94%

2. Index Service (GSI)

  • Mantém Índices Secundários Globais (Standard ou MOI in-memory).
  • Hardware Alvo: Alta RAM + Discos NVMe ultrarrápidos.
Throughput NVMe / RAM Scan89%

3. Query Service (N1QL)

  • Parser, otimizador de custo (CBO) e executor de queries SQL++.
  • Hardware Alvo: Múltiplos núcleos de CPU (Compute-heavy).
Processamento Paralelo CPU91%

4. Search Service (FTS)

  • Índices invertidos (Bleve) e Vector Search (IA/RAG) integrados sem precisar de Elasticsearch externo.

5. Analytics Service

  • Motor MPP colunar para queries OLAP complexas com isolamento total (Zero impacto nos nós KV).

6. Eventing Service

  • Funções Serverless em JavaScript (V8) disparadas em tempo real por mutações via stream DCP.
Slide 9 • Consultas Declarativas e Indexação Global

Couchbase: Hierarquia Lógica, N1QL (SQL++) e Índices GSI

O poder do ANSI SQL aplicado nativamente a documentos JSON aninhados

🗂️ Mapeamento Relacional e Recursos SQL++

  • Hierarquia 3 Níveis: Bucket (DB) ➔ Scope (Schema) ➔ Collection (Tabela).
  • ANSI JOINs Nativos: INNER JOIN, LEFT JOIN entre coleções JSON distintas.
  • Operadores para Arrays JSON: UNNEST (achata arrays internos em linhas), NEST, ARRAY ... FOR ... END.
  • GSI vs. Scatter-Gather: O Query Service consulta apenas o nó GSI relevante e busca documentos exatos (ou resolve 100% via Covering Index).

ORDER BY d.nota DESC;

Slide 10 • Posicionamento Arquitetural: Apache CouchDB

Onde o Apache CouchDB Brilha: O Rei do Offline-First e Edge

A simbiose perfeita entre Apache CouchDB no servidor e PouchDB nos dispositivos

📱 Arquitetura Offline-First (CouchDB + PouchDB)

  • PouchDB: Implementação JavaScript do protocolo CouchDB que armazena dados localmente no navegador (IndexedDB) ou mobile (SQLite).
  • Zero Latência Percebida: A aplicação lê e escreve 100% no banco local, funcionando mesmo sem internet.
  • Sincronização Bidirecional em 1 Linha:
    localDB.sync(remoteCouchDB, { live: true, retry: true })

🛰️ Cenários Ideais de Engenharia

  • Operações de Campo sem Rede: Logística em estradas, plataformas marítimas, aviação, minas subterrâneas e zonas rurais.
  • Edge Computing & IoT: Consumo mínimo de recursos (roda em Raspberry Pi / containers com ~64–128 MB de RAM).
  • Topologias Multi-Site Descentralizadas: Filiais ou navios que operam autonomamente e sincronizam via satélite.

Slide 11 • Mercado e Limitações: Apache CouchDB

Apache CouchDB no Mercado Real e Trade-offs Técnicos

Quem utiliza em produção e quando NÃO escolher o CouchDB

🏆 Casos Reais no Mercado Global

  • Hyperledger Fabric (Linux Foundation): Utiliza o CouchDB como World State Database oficial para Smart Contracts devido à determinicidade e queries JSON.
  • npm Registry: Base histórica de replicação global de metadados de pacotes JavaScript e mirrors offline corporativos.
  • eHealth Africa & Médicos Sem Fronteiras: Rastreamento epidemiológico em campo (combate ao Ebola) em áreas sem conectividade.
  • IBM Cloudant: Oferta DBaaS global na IBM Cloud construída sobre o Apache CouchDB.

⚠️ Trade-offs (Quando Evitar o CouchDB)

  • Mutações de Alta Frequência na Mesma Chave: Atualizar um contador 500x/seg gera explosão da árvore _rev e crescimento acelerado do disco antes do Compaction.
  • Ausência de JOINs e Transações Multi-Documento: Não suporta junções entre documentos distintos no servidor.
  • Custo de Serialização HTTP: Cada operação individual trafega cabeçalhos HTTP, tendo latência maior que protocolos binários em RAM.
Slide 12 • Posicionamento Arquitetural: Couchbase

Onde o Couchbase Brilha: Latência Sub-ms e Escala Global (XDCR)

Consolidando Cache Distribuído + Banco Documental SQL++ em uma única camada

⚡ Fim da Arquitetura Dupla (DB + Cache Externo)

  • Substitui a complexa combinação RDBMS/MongoDB + Redis/Memcached por um único cluster unificado.
  • Elimina bugs de Cache Invalidation, Cache Stampede e dessincronização entre camadas.
  • Cenários Ideais: Gestão de Sessão/Perfil de milhões de usuários, Catálogos de E-commerce, Antifraude em tempo real, Jogos Online e AdTech.

🌍 XDCR (Cross Data Center Replication)

  • Replicação assíncrona Memória-a-Memória entre datacenters ou nuvens distintas (AWS ⇄ GCP ⇄ Azure).
  • Suporta topologias Unidirecionais, Bidirecionais (Active-Active) e filtragem avançada por expressões SQL++.
  • Resolução Automática de Conflitos: Por contagem de revisões (Sequence Number) ou Timestamp com HLC (Hybrid Logical Clocks).

Slide 13 • Mercado e Limitações: Couchbase Server

Couchbase em Escala Extrema e Seus Trade-offs Arquiteturais

Cases de missão crítica (Tier-1) e os custos de infraestrutura Memory-First

🏢 Gigantes que Rodam em Couchbase

  • LinkedIn: Mais de 10 milhões de queries/segundo em clusters Couchbase servindo perfis e conexões com latência < 2ms.
  • Amadeus, Sabre & United Airlines: Sistemas globais de reservas de voos, inventário de assentos e cartões de embarque em tempo real.
  • PayPal & Revolut: Prevenção a fraudes, autenticação e sessões financeiras de baixa latência.
  • Domino's Pizza & Tesco: Processamento de pedidos em picos extremos (Super Bowl / Black Friday).

⚠️ Trade-offs (Quando Evitar o Couchbase)

  • Pegada Pesada de Memória RAM: Exige servidores robustos para manter o Working Set e índices em RAM (16 GB–64 GB+ por nó em produção).
  • Complexidade Operacional (Day-2 Ops): Requer dimensionamento cuidadoso de cotas de serviços MDS, monitoramento de Cache Miss Ratio e rebalanceamento de vBuckets.
  • Licenciamento Enterprise: Recursos avançados (como motor Magma, MOI e certas features de segurança) são exclusivos da edição Enterprise/Capella.
Slide 14 • Matriz Comparativa Arquitetural (Parte 1/2)

Comparativo Direto: Modelo de Dados, Teorema CAP e Consultas

Análise lado a lado das garantias distribuídas e capacidades de manipulação de dados

Dimensão Técnica 🟧 Apache CouchDB 🟦 Couchbase Server
1. Modelo de Dados Documentos JSON + Anexos binários (_attachments). Estrutura plana de Databases sem schemas intermediários. Documentos JSON + KV Binário. Hierarquia relacional em 3 níveis: Bucket ➔ Scope ➔ Collection.
2. Teorema CAP / PACELC AP (Availability + Partition Tolerance) (PC/EC): Prioriza disponibilidade contínua e consistência eventual entre réplicas. CP por padrão (PC/EC): Um único vBucket ativo por chave garante consistência imediata (Read-Your-Own-Writes).
3. Concorrência e ACID MVCC otimista explícito via árvore _rev no nível do documento. Sem transações multi-documento. CAS otimista + Lock pessimista opcional + Transações ACID Distribuídas Multi-Documento.
4. Mecanismos de Consulta Views pré-computadas (MapReduce em JS/Erlang) e Mango Queries (_find) em JSON. Não possui JOIN. N1QL / SQL++ (SQL for JSON) com ANSI JOIN, UNNEST, GROUP BY, CTEs + Full-Text e Vector Search.
Slide 15 • Matriz Comparativa Arquitetural (Parte 2/2)

Comparativo Direto: Replicação, Latência e Complexidade

Como escolher a ferramenta certa para o SLA e a infraestrutura do projeto

Dimensão Técnica 🟧 Apache CouchDB 🟦 Couchbase Server
5. Mecanismos de Replicação Couch Replication Protocol sobre HTTP (_changes + _revs_diff). Nativo para P2P, Edge e navegadores via PouchDB. DCP (intra-cluster) e XDCR (inter-cluster) via stream binário TCP de memória para memória. Mobile requer Sync Gateway + Couchbase Lite.
6. Performance e Latência Latência em milissegundos (5ms–30ms+), limitada por I/O de disco append-only e overhead de HTTP/JSON. Latência sub-milissegundo (< 1ms / microssegundos) para operações KV em RAM e poucos ms para queries SQL++ com GSI.
7. Complexidade Operacional Baixa Infraestrutura: Roda com pouca RAM, API 100% HTTP sem SDK obrigatório. Exige atenção a Compaction e conflitos _rev. Engenharia Enterprise: Exige dimensionamento de RAM (Working Set), topologia MDS (Data/Index/Query) e SDK binário.

Quiz Arquitetural (Clique na alternativa para revelar o gabarito)

Questão 1: MVCC (_rev) no CouchDB

Dois clientes leem _rev: "1-abc". O Cliente A atualiza para 2-def. Um ms depois, o Cliente B envia PUT ainda com 1-abc. O que ocorre?

A) Usa lock pessimista e sobrescreve bytes in-place.
B) Rejeita com HTTP 409 Conflict e mantém escrita append-only até o Compaction.
C) Aceita com Last-Write-Wins via relógio NTP.
D) Faz merge automático de atributos JSON distintos.
E) Grava no vBucket em RAM e resolve no Index Service.
Gabarito: B. O CouchDB exige o _rev atual da folha; revisões obsoletas recebem 409 Conflict imediato e os blocos antigos ficam intactos até o Compaction.

Questão 2: vBuckets no Couchbase

Como o Couchbase Server particiona dados e roteia requisições KV em um cluster de 8 nós?

A) Usa proxies roteadores e ZooKeeper central.
B) Faz shard splitting dinâmico a cada 64 MB via HTTP.
C) Divide o Bucket em 1024 vBuckets (CRC32) e o SDK faz roteamento single-hop via Cluster Map.
